## TLS with Cloudflare proxying and Full (strict)

The existing shared edge must own the `assemblyos.uz` certificate. The internal project Caddy uses HTTP on a private Docker network and never issues a certificate.

The prepared shared-edge site disables TLS-ALPN-01, which cannot reach an origin through Cloudflare's TLS proxy, and leaves HTTP-01 enabled. Before switching proxied DNS to the new origin, configure a narrow exception for `http://assemblyos.uz/.well-known/acme-challenge/*`: no Cloudflare Always Use HTTPS/redirect rule, WAF/bot challenge, Access login, Worker interception, or cache response may prevent the ACME request from reaching the new edge on port 80. Do not weaken the zone's Full (strict) mode. Keep other traffic in maintenance while the certificate is issued. Verify CAA records permit the configured issuer and remove stale AAAA records unless IPv6 is intentionally configured and verified.

Once the approved edge site is loaded, point the proxied A record to `65.108.142.153` and allow HTTP-01 to complete. Confirm successful issuance in edge logs, then run `bash scripts/verify-tls.sh assemblyos.uz 65.108.142.153` from outside the origin. This uses curl certificate verification and SNI with `--resolve`, never `-k`, and then checks public HTTPS. Check certificate subject/SAN, chain and expiry and that Cloudflare is actually in Full (strict), not merely that a browser sees Cloudflare's edge certificate. Test renewal challenge routing too; retain the exception.

If HTTP-01 cannot be made reachable, stop cutover. An approved DNS-01 setup (requires a Caddy DNS provider module and narrowly scoped token) or an approved Cloudflare Origin CA certificate is an alternative; neither has been installed by this change. Do not solve issuance by switching to Flexible/Full without validation. Current direct origin TLS is failing, so issuance is explicitly still pending.

Sources: [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https), [Caddy ACME challenge controls](https://caddyserver.com/docs/caddyfile/directives/tls), [Cloudflare Full (strict) origin requirements](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/).

## Rollback

Before accepting any writes on the target, keep the old database/media unchanged and writers stopped. If target verification/TLS fails, leave target writers/bot stopped, restore the previous shared-edge site configuration with an approved reload if necessary, return DNS to the old origin, wait for propagation, and explicitly approve resuming only old Assembly services/timer. Do not restart old PostgreSQL or alter other projects.

After target writes begin, the old database is stale. Stop target writers, take a fresh project-only backup and plan a separately approved reverse data transfer. Never simply point DNS at the old writable database, never run both bots, and never restore a PostgreSQL 18 dump into PostgreSQL 17 without compatibility review. Keep all critical snapshots and old media until rollback risk is resolved.
